## Pre-flight: Remix setup (read this before opening Remix)

Both testnet nights hit the same handful of Remix/MetaMask footguns repeatedly. None of
them are contract bugs — they're environment traps that cost real time. Check all of
these *before* touching Deploy:

| Check | Correct value | What happens if wrong |
|---|---|---|
| Compiler version | `0.8.20+commit.a1b79de6` | Different bytecode than what was measured/audited |
| Optimizer | **Enabled** | Off → 39,147 bytes, deployment fails outright |
| Optimizer runs | **1** | runs=200 → 24,523 bytes, only 53 bytes of headroom (still fits, but no margin for anything else) |
| **EVM Version** | **`shanghai`** — not `paris`, not default | `paris` alone adds ~450 bytes and pushed the factory *over* the 24,576 limit last night. Base has supported Shanghai opcodes since Jan 2024 (mainnet) / Nov 2023 (Sepolia) — confirmed via Base's own Canyon hardfork docs, not assumed. |
| MetaMask network | **Base** (mainnet, chain ID 8453) | Remix's provider dropdown can silently default to a *different* chain after any refresh — happened twice across two nights. Always re-check both MetaMask's own indicator *and* Remix's Deploy-panel network badge before clicking Deploy, every single time, even mid-session. |
| Remix provider dropdown | Plain **"MetaMask"**, not a specific named chain from the list | The named-chain list may not even include Base if it's never been added to that dropdown's cache; plain "MetaMask" always follows whatever network the extension is actually on. |
| Value field on every write call | **0 wei**, unless the function is explicitly payable (none here are) | A stray nonzero value (seen once, cause unclear) makes an otherwise-correct call revert. Check it every time, not just once. |

**One more thing worth doing before mainnet that wasn't done before testnet:** actually
compile-check the mainnet files fresh in Remix, don't assume yesterday's testnet compile
generalizes. Confirm the factory shows **24,153 bytes** deployed (or check Remix's own
size warning is absent) before deploying real capital against it.

## Deployment sequence

1. **Compile both files** with the settings above. Confirm no size warning appears.
2. **Deploy `SportsbookFactory-v1_4.sol`** with constructor args:
   - `_usdc`: `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`
   - `_oo`: `0x2aBf1Bd76655de80eDB3086114315Eec75AF500c`

   ⚠️ **Do not reuse the Sepolia OOV3 address.** `0x0F7fC5E6482f096380db6158f978167b57388deE`
   is OOV3 on Sepolia but a completely different contract (`AddressWhitelist`) on mainnet —
   a genuine cross-chain address collision, verified against UMA's own network registries
   for both chains. Using it here would silently point the factory at the wrong contract.
3. **Immediately verify, don't assume:** call `settlementIdentifier()` (free, no gas) and
   confirm it returns `ASSERT_TRUTH2`'s bytes32 value — same discipline as every other
   step in this project. If it doesn't match, stop and investigate before going further.
4. **Do not call `createMarket()` yet.** First:
   - Update `CLAUDE.md` / `README.md` with the new factory address (already queued as a
     separate stale-doc fix — good time to combine it).
   - Update the market-opener bot's `FACTORY_ADDRESS` in `.env`. **No ABI change needed**
     — `MarketCreated` and `getMarketInfo()` are byte-identical to v1.3 (see R-2 in the
     delta audit). Verify this yourself: the bot's `chain.ts` event fragment must still
     hash-match the newly deployed contract, not just look similar.
   - **Update the web app's factory address in Vercel** — this is the live one the
     deployed app at evensteven.bet actually reads. Go to the Vercel dashboard →
     Even Steven project → Settings → Environment Variables → find
     `NEXT_PUBLIC_FACTORY_ADDRESS` → update to the new v1.4 address → redeploy.
     No ABI changes needed in the web app either (same byte-identical reason as the bot).
   - Also update the web app repo's `.env.example` with the new address (housekeeping,
     doesn't affect runtime).
5. **Create one real market manually first**, not via the bot — final live sanity check
   on mainnet before the automated opener touches the new factory. Run it through a full
   bet → close → `requestSettlement()` → wait → `executeSettlement()` → `claimPayout()`
   cycle, same shape as the testnet rehearsal, before trusting it with real volume.
6. **Only after that manual cycle succeeds**, resume normal bot-driven market creation.

## What happens to the two stranded markets

`Titans/Seahawks` and `Lions/Commanders` were deployed under the v1.3 factory and run
v1.8.1 bytecode. They are not migrated — they cannot be; the identifier is hardcoded and
the contract has no upgrade path by design (no proxy, immutable contracts, per the
"fully trustless, no owner override" architecture decision from earlier audits).

Handling: once each market's `bettingClosedAt + REFUND_TIMEOUT` (7 days) has passed,
call `triggerRefund()` on each. This returns every bettor's stake — no winners, no
losers, no fee retained on the refunded stakes. **You're handling this in the thread
that originally created those markets — unrelated to this deploy, no action needed here.**
