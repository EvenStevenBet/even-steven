# v1.9 UMA Fix — Testnet Rehearsal Runbook

**Purpose:** prove the v1.9 identifier fix actually works against live UMA
infrastructure before any mainnet redeploy. This is the standing process change from
the Aug 29 incident: static code review is not enough for anything touching UMA —
only a real, live settlement cycle counts as verified.

**Do not skip Step 0.** Everything else in this runbook can pass on testnet while
Step 0 is still unconfirmed, and Step 0 is the one thing that determines whether
mainnet will actually work.

   `Finder` contract at `0x7E6d9618Ba8a87421609352d6e711958A97e2512` — this address

2. Find the function `isIdentifierSupported`.
3. Paste this exact value into the `identifier (bytes32)` input field:
   ```
   0x4153534552545f54525554483200000000000000000000000000000000000000
   ```

   (This is `"ASSERT_TRUTH2"` encoded as a right-padded bytes32 — the same format
   Solidity uses internally.)
4. Click **Query**.
5. **If it returns `true`:** ASSERT_TRUTH2 is confirmed whitelisted. Proceed with the

6. **If it returns `false`:** stop. Do not deploy anything with this identifier. Come

## Step 0b — Check the SEPOLIA whitelist too (NEW — do not skip)

**This is the step that would otherwise make your testnet rehearsal fail for the
wrong reason.** Base Sepolia has a *different* `IdentifierWhitelist` from mainnet,
and it has no DVM support (it uses `MockOracleAncillary`). UMA governance actions
like UMIP-191 propagate to testnets separately — often late, sometimes never. So
`ASSERT_TRUTH2` being live on mainnet says nothing about whether it's live on Sepolia.

If `ASSERT_TRUTH2` is not whitelisted on Sepolia, `requestSettlement()` will revert
during the rehearsal **even though the fix is correct for mainnet** — a false
negative that could make you throw away a working fix.

1. Go to Base **Sepolia** BaseScan, `IdentifierWhitelist` at:
   `0x4da2fD75dd26A8C8A0a8Db892019651344705836`
   (from UMA's official 84532 registry — not the mainnet address.)
2. Call `isIdentifierSupported` with the same value as Step 0:
   `0x4153534552545f54525554483200000000000000000000000000000000000000`
3. Also test the old one:
   `0x4153534552545f5452555448000000000000000000000000000000000000000000`

**Interpreting the result:**

| Sepolia result | What to do |
|---|---|
| `ASSERT_TRUTH2` = true | Ideal. Run the rehearsal exactly as written below. |
| `ASSERT_TRUTH2` = false, `ASSERT_TRUTH` = true | Expected and fine. Deploy the testnet factory, then call `setSettlementIdentifier(0x4153534552545f5452555448...)` **on the testnet factory only**, and run the rehearsal with `ASSERT_TRUTH`. This still proves the mechanism — that the identifier is correctly threaded through and settlement completes. Mainnet still uses `ASSERT_TRUTH2` (already confirmed in Step 0). |
| Both false | Stop and report back. Something is different about Sepolia's UMA setup than expected. |

Note that the middle row is only *possible* because the identifier is now
configurable. Under v1.8.1 there would have been no way to run this rehearsal at all.

## Step 0c — COMPILER SETTINGS (critical, easy to get wrong)

The factory embeds the full market bytecode at compile time, which puts it right up
against the EIP-170 24,576-byte contract size limit. Measured sizes of the exact
files being deployed:

| Settings | Factory deployed size | Result |
|---|---|---|
| Optimizer **OFF** | 39,147 bytes | ❌ **Deployment fails** — 14.5 KB over the limit |
| Optimizer ON, runs=200 | 24,523 bytes | ⚠️ Works, but only 53 bytes of headroom |
| Optimizer ON, **runs=1** | 24,224 bytes | ✅ **Recommended** — 352 bytes of headroom |

**In Remix: Solidity Compiler tab → Advanced Configurations → tick "Enable
optimization" → set runs to `1`.** Use the same settings on testnet and mainnet, and
the same settings when you verify the contract on BaseScan (verification fails if
the settings don't match the deployed bytecode exactly).

Two things to be aware of:
- If you deploy with the optimizer off, the transaction will fail outright. That's
  a wasted deploy, not a silent problem, but worth avoiding.
- 53 bytes of headroom at runs=200 is not a safe margin for any future change.
  v1.3 had 324 bytes; the v1.9/v1.4 changes consumed 271 of them. Whoever adds the
  next feature to either contract needs to re-measure size before assuming it fits.

## Step 4 — Run the full settlement cycle live

This is the part that actually tests the fix — everything above is setup.

1. Call `closeBetting()` on the market (owner only).
2. **Bond check first:** `MIN_BOND` is a hardcoded `100e6` (100 USDC) constant, and
   `requestSettlement()` floors the bond at that value. You need **100 testnet USDC**
   in the calling wallet, on top of whatever you used for the seed and the test bet.
   Circle's Base Sepolia faucet is rate-limited, so plan for this or you'll stall
   mid-rehearsal. If you'd rather not farm the faucet, you can temporarily lower
   `MIN_BOND` in the *testnet* build only — but if you do, note it explicitly and
   recompile with `100e6` for mainnet, because that's a bytecode difference between
   what you tested and what you ship.
3. Call `requestSettlement(proposedSpread)` with some integer inside the market's
   spread bounds, e.g. `7`.
   - **This is the call that reverted under v1.8.1.** If it succeeds, the fix works.
   - Note the `assertionId` from the `SettlementRequested` event.
4. Wait out UMA's liveness window (7200 seconds = 2 hours, per the hardcoded
   `liveness` param in `requestSettlement()`).
5. Call `executeSettlement()`.
   - Confirm `settled()` returns `true` and `finalSpread()` matches what you proposed.
6. Call `claimPayout(0)` (or `claimAllPayouts()`) from the winning bettor's address.
   - Confirm USDC actually lands in the bettor's wallet.

**If every step above completes without a revert, the v1.9 fix is proven end-to-end
against live UMA infrastructure — not just reviewed as code.**
