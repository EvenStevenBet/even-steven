## Blocking prerequisites

1. ~~Live Base Sepolia rehearsal~~ — **COMPLETED Sept 17, 2026, PASSED.** Full cycle on
   Base Sepolia with real 7,629s UMA liveness: relay-submitted `placeBetFor` recorded the
   EIP-3009 signer as `bettor`, fee routed exactly, seed returned at settlement, agent
   self-claimed exactly 2× stake. Re-verifiable from chain at any time with
   `node scripts/sepolia-rehearsal.mjs verify` (no transactions) — 32/32.
   Details and transaction hashes in `audits/audit-september-2026-delta.md`.

   Original requirement, for reference — harness is written and dry-run validated:
   `scripts/sepolia-rehearsal.mjs` (`npm install` in `scripts/`, then `phase1`, wait ~2h for
   UMA liveness, then `phase2`). It needs a funded Base Sepolia key —
   **~102 USDC + gas, of which the 100 USDC UMA bond is returned after settlement.**
   It deploys all three contracts, has an agent sign an EIP-3009 authorization, has a
   *separate* relay submit `placeBetFor`, asserts from decoded receipts that the signer owns
   the bet, settles through UMA, and has the signer claim directly.

   **Two Base Sepolia facts the harness handles — both verified on-chain, both of which
   would otherwise make a correct build look broken:**
   - Sepolia USDC reports `name() == "USDC"`; mainnet reports `"USD Coin"`. The EIP-712
     domain differs, so a signature built with the mainnet name is invalid on Sepolia.
   - **`ASSERT_TRUTH2` is NOT whitelisted on Base Sepolia — `ASSERT_TRUTH` is. The exact
     inverse of mainnet.** The factory ships defaulting to `ASSERT_TRUTH2`, so the harness
     calls `setSettlementIdentifier("ASSERT_TRUTH")` before creating the test market.
     **Do not carry that call over to mainnet.** Without it, Sepolia settlement reverts in
     precisely the way the v1.8.1 bug did.

2. **Confirm `ASSERT_TRUTH2` is still whitelisted** on Base mainnet via
   `IdentifierWhitelist.isIdentifierSupported()`. **Re-confirmed `true` on Sept 14, 2026**
   against Base mainnet's live `IdentifierWhitelist` (`0xAd517D72B9Cd31F578197D5e903d041B88c69795`,
   resolved through the Finder at `0x7E6d9618Ba8a87421609352d6e711958A97e2512`);
   `ASSERT_TRUTH` returns `false`, confirming from both directions. Note mainnet
   `oo.defaultIdentifier()` *still* returns the non-whitelisted `ASSERT_TRUTH` — which is
   exactly why v1.9 made the identifier a parameter. Re-check on the day of deploy anyway.
3. ~~Decide R6-6~~ — **DECIDED Sept 14, 2026: virtual-seed fix adopted and shipped.**
   Seedless markets' Z now matches seeded markets' Z at every stake size, and seeded
   markets are unchanged from v1.9. See `audits/audit-september-2026-delta.md` R6-6.
4. ~~Decide the launch seed value~~ — **DECIDED Sept 14, 2026: launch at 1 USDC per side**,
   i.e. the bot passes `1000000`. This keeps the contract deploy a one-variable change: the
   web app and the x402 endpoints need no modification at all to work against v1.5.

   **Do not launch seedless yet.** `Web App/lib/payout.ts` hardcodes
   `PROTOCOL_SEED = 1_000_000` and subtracts it from the winning-side denominator instead of
   reading `protocolSeedTotal` from chain. That constant feeds the bet slip,
   `/api/bet/quote` and `/api/markets/agent`. Against a seedless market it subtracts a seed
   that does not exist and **over-quotes** — +1% on deep pools, +25% on thin ones, and a
   1 USDC bet on an empty side displays a **$0 payout**. Over-quoting promises money
   settlement will not pay. See R6-8 in `audits/audit-september-2026-delta.md`.

   Sequencing: ship v1.10/v1.5 seeded → fix `payout.ts` to read `protocolSeedTotal / 2`
   (or drop the workaround entirely, since v1.10's on-chain `getMarketEV` is now correct)
   → verify against a live seeded market → only then flip the bot to `0`.

## Pre-flight: Remix setup

Identical discipline to the v1.9 deploy. Re-check every row **every time**, including
mid-session.

| Check | Correct value | What happens if wrong |
|---|---|---|
| Compiler version | `0.8.20+commit.a1b79de6` | Different bytecode than what was measured and audited. Note: a stray toolchain can silently substitute 0.8.26 — this happened during the v2 build and invalidated a full round of size measurements. Confirm the exact commit hash, not just "0.8.20". |
| Optimizer | **Enabled** | Off → deployment fails outright |
| Optimizer runs | **1** | Higher runs inflate size; the whole point of the split is headroom, don't spend it here |
| **EVM Version** | **`shanghai`** — not `paris`, not default | `paris` adds ~450 bytes. Base has supported Shanghai opcodes since Jan 2024 (mainnet) / Nov 2023 (Sepolia). |
| MetaMask network | **Base** (mainnet, chain ID 8453) | Remix's provider dropdown can silently default to a different chain after any refresh — this happened twice during the v1.9 deploy. Re-check MetaMask's indicator *and* Remix's Deploy-panel badge before every Deploy click. |
| Remix provider dropdown | Plain **"MetaMask"**, not a named chain | The named-chain list may not include Base; plain "MetaMask" follows whatever network the extension is actually on. |
| Value field on every write call | **0 wei** (nothing here is payable) | A stray nonzero value makes an otherwise-correct call revert. |

## Deployment sequence

**Order matters.** The factory pins the deployer as an `immutable` at construction, so the
deployer must exist first and cannot be changed afterwards.

1. **Compile** `SportsbookMarket-v1_10.sol`, `MarketDeployer-v1_0.sol` and
   `SportsbookFactory-v1_5.sol` with the settings above. Confirm the three sizes.

2. **Deploy `MarketDeployer`** — no constructor arguments.
   Record the address. Verify on BaseScan immediately.

3. **Deploy `SportsbookFactory`** with:
   - `_usdc` = `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`
   - `_oo` = `0x2aBf1Bd76655de80eDB3086114315Eec75AF500c`
   - `_deployer` = the MarketDeployer address from step 2

4. **Verify the wiring before anything else.** Call `factory.deployer()` and confirm it
   returns exactly the step-2 address. A factory pointed at the wrong deployer would mint
   markets running arbitrary code — this is the one genuinely new failure mode in this
   release.

5. **Confirm `factory.settlementIdentifier()`** returns `ASSERT_TRUTH2`, and that the
   identifier is still whitelisted on Base mainnet.

6. **Approve USDC** for the factory from the production wallet:
   `type(uint256).max` (Circle USDC on Base rejects exact-amount approvals intermittently).
   Required at the 1 USDC launch seed; only skippable if the seed is ever set to 0.

7. **Create one small test market** with the launch seed:
   `createMarket("<gameId>", <oracleZ>, 1000000)` — 1 USDC per side.
   The factory pulls `seed * 2` from the caller, so step 6's max approval must be done first.
   Confirm `MarketCreated` decodes with the same topic0 as v1.4
   (`0xb0986a0038b9a2afc3b9dc7e400ddeb31ff547737cf738390752e5e6eba767a5`) — the bot depends
   on this.

8. **Smoke-test both bet paths on mainnet with small real amounts:** one `placeBet` and one
   `placeBetFor` submitted from a *different* address than the signer. Confirm from the
   decoded `BetPlaced` that `bettor` is the signer, and that the relay's USDC balance is
   unchanged.

9. **Verify all three contracts on BaseScan** (Exact Match).

10. **Only then** update `FACTORY_ADDRESS` in Vercel env and the bot `.env`.

## Carried over from the live rehearsal

Two operational notes, neither requiring a change to the deployment steps above:

- **R6-9 — the production wallet already holds ETH, but note the asymmetry.** An agent
  betting through `placeBetFor` needs no gas; claiming its payout requires native ETH.
  This affects the `POST /api/bet` thread and agent-facing docs, not this deploy.
- **R6-10 — keep the RPC read-your-writes consistent.** Step 6 (`approve`) → step 7
  (`createMarket`) is exactly the sequence that failed repeatedly on a load-balanced public
  endpoint, because viem simulates before sending and a lagging node sees no allowance.
  Deploy through Remix/MetaMask against a consistent provider, and if step 7 reverts with
  "transfer amount exceeds allowance", re-read the allowance before assuming anything is
  wrong — the approval has almost certainly landed.

## Rollback / abort conditions

Abort and do not proceed if any of these occur:

- Any of the three contracts reports an EIP-170 size warning in Remix
- `factory.deployer()` does not exactly match the deployed MarketDeployer address
- `ASSERT_TRUTH2` is not whitelisted on Base mainnet at deploy time
- `MarketCreated` topic0 differs from v1.4's
- The `placeBetFor` smoke test records the relay — not the signer — as `bettor`
- The relay's USDC balance changes during the `placeBetFor` smoke test

**Rollback is clean.** v1.4 stays live and untouched throughout; markets already created by
it keep working and settling independently. Nothing about this deploy migrates or disturbs
existing markets. If v1.5 is abandoned, point the bot and app back at v1.4 and nothing is
lost but gas.
